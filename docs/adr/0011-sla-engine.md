# ADR 0011: SLA engine — per-priority policies, delayed-job breach checks, no timezone dependency

## Status

Accepted, implemented.

## Context

The last open item from Phase 2's original planning note ("`SlaPolicy` + `BusinessHours` + breach escalations") after Macros shipped. Two real questions had to be answered before writing any code: how a tenant defines what "on time" means, and how a breach actually gets noticed and acted on.

## Decisions

**One `SlaPolicy` row per (tenant, priority) — not a general rule-based policy engine.** A policy is looked up directly by the ticket's current `priority`; there's no matching on team, channel, or any other condition. A priority with no policy row gets no SLA tracking at all — opt-in by construction, not a "misconfigured" state. This is the same YAGNI call made on custom fields (no typed mirror table) and macros (no categories): nothing yet needs per-team or per-channel targets, and a rule-matching engine is real complexity to carry with no evidence it's needed.

**Due dates live directly on `Ticket`** (`firstResponseDueAt`, `firstRespondedAt`, `resolutionDueAt` — `resolvedAt` already existed), not a separate tracking table. A ticket's SLA state is 1:1 with the ticket itself; a join table would only add a lookup for no benefit. `firstRespondedAt` is stamped once, in `addMessage`, the first time an agent posts a non-private reply — never overwritten by a later reply, and never set by an internal note (same "internal notes don't count as customer-facing activity" rule already applied to email sending and webhook dispatch).

**A priority change restarts the clock from *now*, not from the ticket's original creation.** `updateTicket` recomputes both due-ats from the current instant whenever `priority` actually changes (guarded so patching, say, just the assignee never touches an already-running clock). The reasoning: the ticket's urgency was just reclassified, so how long it's *allowed* to take should measure from that reclassification, not penalize (or credit) it for time that passed under the old, presumably-wrong priority.

**Business-hours math uses no timezone library — `Intl.DateTimeFormat` only, with a documented limitation.** `packages/shared/src/sla.ts`'s `addBusinessMinutes` computes a UTC offset once via `Intl` at the start of a calculation and holds it constant for the whole walk forward. This means a calculation that straddles a real DST transition in that timezone will be off by the transition's shift (usually 60 minutes) for the part of the walk past it. Accepted deliberately rather than pulling in a timezone dependency mid-session: SLA windows are typically hours to a few days, DST-straddling is rare, and the failure mode is a due date off by an hour, not a security or correctness issue. `BusinessHoursSchedule` itself is one optional `{start,end}` window array per weekday, stored as jsonb on `BusinessHours` (jsonb here because 14 nullable time columns would be more code for the same validated-at-the-boundary shape, not because the shape is genuinely flexible — same reasoning as `Macro.actions`).

**Breach detection is two-layered: passive (always correct) and active (a webhook, best-effort).**
- *Passive*: `apps/web/src/lib/format.ts`'s `isFirstResponseOverdue`/`isResolutionOverdue` compare the stored due-at against `now()` at render time. This is what the red "First response overdue" / "Resolution overdue" badges and the ticket queue's clock icon show — always accurate, because it's computed fresh every render, never a stale cached flag.
- *Active*: a delayed BullMQ job (`SLA_BREACH_QUEUE_NAME`), one per milestone, scheduled at ticket creation and again whenever a priority change moves the due-at. The job's delay is `dueAt - now` at schedule time, but it **re-reads the ticket fresh when it fires** and re-checks against the ticket's *current* state before doing anything — if the milestone was met, or the due-at moved (a later priority change rescheduled its own job independently), the fire is a silent no-op. This means a stale job is never wrong, only sometimes redundant-and-harmless. Two new webhook events, `sla.first_response_breached` and `sla.resolution_breached`, reuse the entire existing webhook infrastructure (ADR 0009) — signing, retries, delivery-status bookkeeping — none of it duplicated.

**The worker duplicates a small webhook-dispatch helper rather than importing from `apps/api`.** `apps/worker/src/lib/webhookDispatch.ts` mirrors `apps/api/src/lib/webhookDispatch.ts` almost line for line. This is the same boundary `apps/worker/src/webhooks/deliver.ts` already respects (it queries Prisma directly rather than calling into `apps/api`'s ticket service) — each deployable app stays self-contained, and ~15 duplicated lines is cheaper than coupling two separately-deployed processes' source trees together.

**Read/write permission split, same as every other tenant-configuration feature this session.** `GET /sla-policies` and `GET /business-hours` are `tickets:read` (any agent can see why a ticket looks overdue); `PUT`/`DELETE` are `tickets:manage_all`. Caught correctly on the first pass this time — the mistake had already been made and fixed three times before (custom fields, process templates, macros).

## Verified

7 new integration tests (`apps/api/test/sla.test.ts`) against real Postgres: a ticket created with no matching policy gets null due-ats; one created after a policy exists gets correct calendar-time due-ats (asserted within a small tolerance of `Date.now()`, not hardcoded); a priority change recomputes due-ats from the moment of the change, and an unrelated patch (assignee) never touches an already-set due-at; a business-hours-gated policy's resulting due-at genuinely falls inside the configured weekday/hour window; `firstRespondedAt` is stamped once by the first public reply and never touched by an internal note or a later reply. Plus 6 pure-function tests (`packages/shared/src/sla.test.ts`) for `addBusinessMinutes` covering: a same-day case, starting before the window opens, a same-day gap between two windows (lunch break), rolling over a weekend with no configured window, and a fixed-offset (non-UTC) timezone changing which local weekday a UTC instant falls on. Full `apps/api` suite 29/29 passing (skipped tests are pre-existing, opt-in tenant-isolation tests unrelated to this change), `apps/api` and `apps/worker` both typecheck clean.

Beyond automated tests, directly against the real running app: configured a Business Hours schedule and an SLA policy for LOW priority through the browser, confirmed both persisted after a reload; created a real ticket through the API and confirmed it picked up the configured LOW-priority due-ats; backdated a real ticket's due-ats in Postgres (simulating time having passed, since waiting out a real SLA window isn't a practical verification step) and confirmed both the ticket-detail header badges and the DETAILS panel's red "Due"/overdue styling, and the tickets-queue clock icon, all rendered correctly — zero console errors throughout.

**A real infrastructure bug was caught and fixed during this pass, unrelated to the SLA code itself**: the running dev API server had accumulated multiple stale, orphaned `tsx watch` processes across the session (each restart leaving the previous one alive, still bound to nothing after the first one wins the port), and separately a genuinely stuck node process actually holding port 4000. The `/auth/login` route's error handling — deliberately generic (`catch { return reply.code(401).send({ error: 'invalid credentials' }) }`, to avoid leaking whether a tenant/email/password specifically was wrong) — masked a `DATABASE_URL` credential mismatch on one restart as an ordinary wrong-password error, which took directly verifying the bcrypt hash and the Postgres role's password outside the app to diagnose. Worth remembering: a security-motivated generic error message is exactly the kind of thing that also hides real infrastructure failures from whoever's debugging them.

## Consequences / known v1 limitations

- No per-team or per-channel SLA policies — see "one row per (tenant, priority)" above.
- `addBusinessMinutes`'s DST-transition imprecision (see above) — a due date computed across a DST boundary in a DST-observing timezone can be off by the transition's shift.
- Business Hours UI supports exactly one window per day (no split lunch-break schedules) — the underlying `BusinessHoursSchedule` type already supports an array of windows per day; only the settings page's form is scoped down for v1.
- No breach *escalation* beyond a webhook event — no automatic priority bump, no reassignment, no reminder cadence. A tenant's own automation (subscribed to the new webhook events) is the extension point, consistent with the plugin/extension recommendation in `docs/ROADMAP.md`.
- The active (webhook) breach check depends on a live `apps/worker` process consuming `SLA_BREACH_QUEUE_NAME`; if the worker is down when a job fires, BullMQ retains the job (nothing is silently lost) but the webhook fires late, whenever a worker next comes up. The passive UI badges are never affected by worker liveness.
